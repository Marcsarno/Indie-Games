# Procedural / Programmatic Techniques for Pixel-Art Game Characters (for a browser JS isometric ARPG)

Context: the end user's current renderer draws characters from 2D primitives (ellipses, lines, polygons) into a material buffer, applies edge-based shading, then black outlines. These notes cover what better techniques exist and how feasible they are in Canvas 2D / WebGL / three.js. Research done October 2026. About 20 tool calls; some primary sources (t3ssel8r's own videos, Spritec, Houdini pixel renderer, Sprite Lamp internals) could not be fetched. See the Gaps sections.

## 1. 3D-to-pixel-art pipelines (Dead Cells, t3ssel8r-style, Pixelat3D, outline shaders, stability)

### Takeaway
The shipped, proven approach is Dead Cells'. Model and skeleton-animate in 3D, render each frame at final sprite size (about 50 px tall) with anti-aliasing off, export a normal map with every frame, and shade with a toon shader. Outlines come from depth and normal discontinuities in a post pass. The main unsolved artifact is frame-to-frame pixel flicker. Dead Cells shipped with it. Under perspective, camera snapping only fixes it for orthographic cameras. That helps this project, because an isometric ARPG camera is orthographic, which is exactly where snapping works.

### Cited Findings
**Dead Cells (Motion Twin), from Thomas Vasseur's own Game Developer article**
- Pipeline: a 2D pixel-art model sheet, then a 3D model and skeleton in 3DS Max, exported as FBX. A homebrew tool ("Cruncher") renders the mesh at very small size with no anti-aliasing to get the pixelated look. — [Game Developer, Vasseur](https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-)
- In-game characters are about 50 pixels tall. Each frame is exported as a PNG along with its normal map, and "a basic toon shader" uses the normal maps to render volume. Exporting frame sequences also let them add blend modes. A lighting system handles shadows, where the earlier prototype (ScarKrow) needed hand-drawn shadows on every frame. — [Game Developer, Vasseur](https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-)
- Animation is keyframed pose-to-pose like 2D, with interpolation frames added only before or after keyframes, "never in between". Attacks lean on VFX to sell impact. — [Game Developer, Vasseur](https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-)
- Benefits: retakes can be done "dozens of times in minutes". Equipment such as armor attaches to an existing model. Old monster components were reused on new monsters, saving "hundred of hours". — [Game Developer, Vasseur](https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-)
- Pitfalls: **flickering pixels were never fully solved**, and they chose not to hand-clean frames so the workflow stayed fast. Level of detail is low, a trade-off accepted in favour of animation. Vasseur was the sole artist for a year. — [Game Developer, Vasseur](https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-)
- 80.lv's interview says the models and animations were made in 3DS Max by one person and rendered to sprites with an in-house tool. — [80.lv interview](https://80.lv/articles/interview-with-the-developers-of-dead-cells)
- Indie developers have reimplemented "the same pipeline as Dead Cells" as standalone 3D-to-sprite converters. — [midgelf itch.io](https://midgelf.itch.io/3d-to-2d-animations)

**t3ssel8r-style real-time 3D pixel art**
- I found no primary write-up of t3ssel8r's rendering method. His Cascadeur interview covers animation only. He says, "Because we are targeting a pixel art look, our models are quite simple and low in fidelity", with short animations. — [Cascadeur interview](https://cascadeur.com/blog/general/making-an-animation-for-a-3d-pixel-art-game); also [80.lv animation tips](https://80.lv/articles/tips-on-convincing-animations-for-3d-pixel-art-games)
- Third-party descriptions of the "t3ssel8r style" (an Unreal Fab plugin that is not affiliated with him): render the 3D scene at low resolution and upscale natively. Use separate outline controls for **silhouette lines** and **inner crease lines**. "Smart sampling and snapping" removes pixel creep and jitter. — [Fab listing](https://www.fab.com/listings/816f34f2-1a2e-4910-b3dd-009b5da0873b)
- A video explainer ("Drawing the Line on 3D Pixel Art") argues that objects need explicit outlines. Anti-aliasing smooths edges that should stay sharp, and outlines based on color alone can't distinguish true object boundaries. — [SozAI transcript](https://sozai.app/transcript/drawing-the-line-on-3d-pixel-art-pixel-perfect-transcript/index.md)

**Concrete outline and highlight post-shader (leopeltola, Godot; the most-copied implementation of the look)**
- Depth edges: convert raw depth to view-space depth via the inverse projection. Sample the 4 orthogonal neighbours at 1-texel offsets and accumulate only neighbours that are *farther*: `depth_diff += clamp(du - depth, 0., 1.)`, then `smoothstep(0.2, 0.3, depth_diff)`. This mask darkens the pixel (outline) on the *near* side of a silhouette. — [godotshaders](https://godotshaders.com/shader/3d-pixel-art-outline-highlight-post-processing-shader/)
- Normal (crease) edges: decode normals at the centre and 4 neighbours. `normalDiff = dot(baseNormal - newNormal, normalEdgeBias)` with bias `vec3(1,1,1)` and `normalIndicator = smoothstep(-.01,.01,normalDiff)`. Contribution is `(1 - dot(baseNormal,newNormal)) * depthIndicator * normalIndicator`. Sum the 4, apply `smoothstep(0.2,0.8)`, then subtract a "negative depth" mask so highlights don't leak outside the object. The directional bias makes only one side of a crease light up, which reads as a lit edge. — [godotshaders](https://godotshaders.com/shader/3d-pixel-art-outline-highlight-post-processing-shader/)
- Colour application: highlight = `mix(orig, white, 0.1)` where a crease is detected. Shadow or outline = `mix(orig, black, 0.4)` where a depth edge is detected. So the outline is a darkened shade of the underlying colour, not pure black. The author advises moving the camera in 1-pixel increments to avoid jitter. — [godotshaders](https://godotshaders.com/shader/3d-pixel-art-outline-highlight-post-processing-shader/)
- A variant exists because the original depth comparison is absolute and breaks at long distances. — [godotshaders long-distance fix](https://godotshaders.com/shader/3d-pixel-art-outline-highlight-shader-fix-for-long-distance/)

**Pixelat3D (SBGames 2026, Ribes, Maciel and Torchelsen, UFRGS/UFPel)**
- Real-time shader with two stages: (1) screen-space texture processing that lowers texture LOD with distance and view angle, guided by an artist-authored grayscale **priority map**; (2) a post-process outline. The scene is rendered at high resolution and then downscaled. A user study (n=62) showed a significant preference across most scenarios. — [SBGames paper PDF](https://sol.sbc.org.br/index.php/sbgames/article/download/45414/45175/)
- Texture LOD is snapped to power-of-two reductions (`Scale = Dim / 2^I`, I clamped to 0..4, so at most 1/16) to avoid mixels. Each reduced "quadrant" takes the colour of the **highest-priority texel** within it rather than an average, so important features survive downsampling. At grazing angles (via N·V) it swaps in an artist-made low-fidelity texture or a solid colour. — [SBGames paper PDF](https://sol.sbc.org.br/index.php/sbgames/article/download/45414/45175/)
- Outline: a pixel is an outline if any of its 4 or 8 neighbours is *closer* to the camera by more than a threshold (citing King 2018). The outline is drawn with "a darker shade of the closest color". 8-neighbour mode catches diagonal-adjacent edges that 4-neighbour mode misses. — [SBGames paper PDF](https://sol.sbc.org.br/index.php/sbgames/article/download/45414/45175/)
- The paper's related work cites 3D-stable dithering: Pope 2017 maps a dither matrix onto a world-fixed sphere, which handles rotation but not translation; Johansen 2025 stabilises dither on surfaces with a camera-adaptive matrix. It also cites Moreira et al. 2022, normal maps to improve 2D pixel asset quality. — [SBGames paper PDF](https://sol.sbc.org.br/index.php/sbgames/article/download/45414/45175/)

**Stability and pixel crawl**
- "Texel Splatting: Perspective-Stable 3D Pixel Art" (Dylan Ebert, arXiv 2603.14587, March 2026) states the core problem: under perspective, "Pixels at different depths drift at different rates, and no single snap corrects all depths." Grid-snapping the camera works under **orthographic** projection, where every pixel shifts equally. The proposed fix renders geometry into a cubemap from a fixed, grid-snapped world point and splats each texel to screen as a world-space quad. The open problem is disocclusion at probe boundaries. — [arXiv](https://arxiv.org/abs/2603.14587)

**Tools, all of which do essentially low-res render, palette and outline**
- Free and open-source Godot 4.4 "Pixel Renderer" by BUKKBEEK (3D to pixel-art sprite export). — [80.lv](https://80.lv/articles/free-open-source-3d-to-pixel-art-toolkit-for-godot); [Digital Production](https://digitalproduction.com/2025/07/30/godot-pixel-renderer-get-a-free-3d-to-pixel-art-export-toolkit/)
- Sprite Press imports .glb/.gltf/.fbx/.obj and renders through a pixel pipeline with palette controls, outlines and animation capture. — [itch.io](https://thespritewizard.itch.io/sprite-press)
- Blender options: Astropulse "BlenderToPixels", Pixel Kit one-click renderer, and BlenderNation's "Rendering advanced pixelart". — [Gumroad](https://astropulse.gumroad.com/l/BlenderToPixels); [Superhive](https://superhivemarket.com/products/pixel-kit---one-click-pixel-art-renderer/docs); [BlenderNation](https://www.blendernation.com/2021/02/08/rendering-advanced-pixelart/)

### Inferences
- **The best fit for this project:** keep the procedural approach but move it into a tiny three.js / WebGL scene. Build characters from primitives (capsules, spheres, boxes, extruded shapes) parented to a skeleton. Render with an **orthographic** camera at the isometric angle into a low-res `WebGLRenderTarget` (e.g. 64×64 per character, or the full game at 1/3 to 1/4 resolution) with `antialias:false`, and use `NearestFilter` and `magFilter=NearestFilter` when blitting to the canvas. Use MRT (WebGL2 `drawBuffers`) or a second pass to output colour/material ID, normal and depth. Then a post pass does (a) toon ramp lighting from the normal (2 to 4 bands), (b) a depth-edge outline (farther neighbour means outline on the near pixel), and (c) a normal-crease highlight. That is the Dead Cells and t3ssel8r recipe, and every step is standard WebGL. It replaces the current "edge-based shading" with real form shading, because normals come from 3D geometry.
- **Two modes:** (1) *bake* sprite sheets offline or at load time for 8 or 16 directions × N frames (cheap at runtime, as in Diablo); or (2) *render live* every frame. Live rendering allows unlimited directions, equipment combos and smooth IK. It is feasible in browser for dozens of characters if each renders into a small target. A shared atlas render target with viewport/scissor per character keeps draw calls low.
- **Flicker mitigation:** snap the character's root position and camera to the low-res pixel grid, and render each character at an integer pixel offset in its own target. Use consistent model-space orientation quantised to the chosen direction count. Keep thin parts (fingers, weapon tips) at least 1 to 2 output pixels thick at the target scale. Consider a hysteresis rule (a pixel changes only if the new value differs by more than a threshold from the last frame) when baking. Dead Cells shipped with residual flicker, so some is tolerable.
- Use *material/palette index* as the colour output, not RGB. That makes palette swapping and "darker shade of the same colour" outlines (Pixelat3D, leopeltola) trivial: look up a per-material ramp row.

## 2. Voxel-based sprites and SDF/raymarched characters at low resolution

### Takeaway
Voxel to iso sprite is a proven route with tools that export directly (MagicaVoxel iso export, IsoVoxel, PixVoxel). But .vox models aren't rigged, so animation means rendering per-frame poses or splitting the model into rigid voxel parts on a skeleton. I found no well-documented shipped example of SDF/raymarched characters rendered to low-res pixel sprites in this session.

### Cited Findings
- MagicaVoxel can export isometric sprites (added in version 0.96.1) plus OBJ and 2D sprites. Users report the built-in iso export adds border outlines that are hard to disable. — [3dart.it](https://www.3dart.it/en/pixel-art-3d-con-magicavoxel-winmac-2/); [Godot Q&A](https://ask.godotengine.org/13790/voxel-file-to-2d-sprite-sheet-to-be-used-in-2d-rpg)
- **IsoVoxel** (Tommy Ettinger, open source) generates isometric pixel art from .vox files. A newer version adds four diagonal-direction renders with **sloped voxels** to soften hard edges. **PixVoxel** generates 8-direction iso sprites for a wargame. — [ecosyste.ms IsoVoxel](https://awesome.ecosyste.ms/projects/github.com%2Ftommyettinger%2FIsoVoxel); [OpenGameArt PixVoxel](https://lpc.opengameart.org/comment/32699)
- MagicaVoxel models "can't be animated as 3D models". Developers render frames themselves, and one automated conversion of every asset into PNGs for 4 angles because doing it by hand was slow. — [itch.io devlog: Converting .vox files to isometric images](https://fluffy-lotus.itch.io/secret-of-the-basilisk/devlog/45370/converting-vox-files-to-isometric-images); [OpenGameArt](https://opengameart.org/node/35819)

### Inferences
- In JS, a voxel character can be built procedurally (fill a 3D grid from primitive shapes: ellipsoids for torso and head, cylinders for limbs), split into rigid body-part grids, posed by a skeleton, and rendered either as instanced cubes in three.js or by CPU projection. For an iso view with 1 voxel ≈ 1 to 2 screen pixels, a CPU "splat" with a z-buffer is simple and fast in Canvas 2D (ImageData). Per-voxel face normals give 3-tone iso shading (top, left, right) for free, which is the classic look and much better form-reading than 2D edge shading.
- An SDF approach is a natural upgrade of the user's existing ellipse/line primitives. Model body parts as SDF capsules and ellipsoids with smooth-min blending, raymarch in a fragment shader into a small (e.g. 48×64) target, and take normals from the SDF gradient. This yields organic silhouettes and correct normals for toon shading. Cost is trivial at sprite resolutions. Treat it as a credible technique without a cited shipped example.

### Gaps
- No primary-source case study of a shipped game rendering SDF characters to pixel sprites was found.
- I didn't verify specific commercial games that use voxel-to-iso sprite pipelines.

## 3. 2D normal-map shading of sprites (Sprite Lamp, Laigter, SpriteIlluminator) and generated normals

### Takeaway
Normal maps let flat sprites take dynamic lights with correct form shading. Dead Cells used per-frame normal maps exported from 3D with a toon shader. Tools generate them from art: Laigter does it automatically, Sprite Lamp from hand-drawn light profiles. For procedurally drawn primitives you can compute exact normals analytically, which beats any generator.

### Cited Findings
- Dead Cells exports a normal map per frame and uses a toon shader on it to render volume and support dynamic lighting. — [Game Developer, Vasseur](https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-)
- **Laigter** (azagaya, open source, Flathub) is an automatic normal-map generator for 2D sprites. Drag and drop an image to get normal, parallax, specular and occlusion maps, with a real-time lighting preview. — [Laigter docs](https://laigter.readthedocs.io/en/latest/Introduction/intro.html); [LinuxLinks](https://www.linuxlinks.com/laigter-generate-lighting-maps-2d-game-artwork/); [Flathub](https://flathub.org/apps/io.itch.azagaya.Laigter)
- **Sprite Lamp** creates normal maps from hand-drawn art and ships "fully commented" GLSL shaders that can be used as a base in your own game. **Sprite DLight** does one-click generation. **Unflattener** is a free open-source Python tool for sprite normal maps. — [AlternativeTo: Sprite Lamp](https://alternativeto.net/software/sprite-lamp); [Steam](https://store.steampowered.com/app/316830?l=french); [Esoteric forum, Sprite DLight](https://uk.esotericsoftware.com/forum/d/3770-dynamic-lighting-with-sprite-dlight); [AlternativeTo: Unflattener](https://alternativeto.net/software/unflattener)
- Academic: Moreira et al. 2022 uses normal maps to improve pixel-art asset quality (cited in the Pixelat3D related work). — [SBGames paper PDF](https://sol.sbc.org.br/index.php/sbgames/article/download/45414/45175/)

### Inferences
- **Analytic normals for the user's primitive renderer** are the highest-leverage, lowest-cost change. For each primitive written into the material buffer, also write a normal:
  - Ellipse (a body part seen as a spheroid): at local pixel (x, y) with semi-axes (a, b), let u=x/a, v=y/b, then z=sqrt(max(0,1-u²-v²)) and N=normalize(u/a, v/b, z/c). This is a "sphere impostor".
  - Thick line or limb (capsule): N comes from the perpendicular distance to the segment axis (cylinder normal), with spherical caps.
  - Polygon (armour plate or blade): a constant tilted normal, or a bevel normal near the edges from a distance transform.
  - Also write depth (z = base depth + height), which then enables depth-based outlines between overlapping parts (e.g. an arm in front of the torso) instead of drawing black outlines around every primitive.
- Generated normals from a height map: build height from a distance transform of each part's mask (height = f(dist to edge), e.g. sqrt for rounded, linear for bevelled), blur lightly, then take N = normalize(-dh/dx, -dh/dy, k). That is roughly what automatic tools like Laigter do (unverified internals).
- Shading: light with N·L, then quantise to 2 to 4 bands via a per-material palette ramp (toon ramp), plus optional rim or crease highlight. Because the output is a ramp index, the result stays on-palette. Edge-based shading only approximates lighting near outlines. Normal shading gives correct terminator lines, light direction consistency across the whole character, and supports torches or spells as dynamic lights in a Diablo-like.
- Pixel-art-specific caution: unconstrained N·L creates noisy single-pixel bands. Quantise, and optionally apply a small majority filter or "min run length" cleanup on the band index.

### Gaps
- Sprite Lamp's exact algorithm for combining the multi-directional lighting profiles and Laigter's height-generation method were not retrieved.
- No source on SpriteIlluminator specifics was retrieved.

## 4. Paper-doll / layered sprite systems and palette swapping

### Takeaway
Diablo II and the LPC generator both compose characters from per-body-part, per-equipment sprite layers with an explicit, sometimes per-direction, draw order. LPC uses JSON item definitions with multiple z-ordered layers per item (e.g. front and back for capes and weapons). Combined with indexed-palette recolouring this gives combinatorial variety cheaply. A 3D or skeletal procedural renderer gets layering "for free" from depth.

### Cited Findings
- **Diablo II:** a character is split into separate layers (weapon, shield, torso, shoulder, etc.), each rendered individually, with a special file giving stacking order. — [Allegro.cc depot](https://www.allegro.cc/depot/utility)
- DCC filenames encode body part, armour type, mode and weapon/hit-class, e.g. "BH TR LIT A1 HTH.DCC". DC6 holds static images and DCC compressed animations. — [Würzburg Diablo II slides](https://wuecampus.uni-wuerzburg.de/moodle/pluginfile.php/1552636/mod_resource/content/1/Diablo%20II.pdf)
- Draw the base body, then armour, weapon, shield and helmet on top rather than prerendering combinations, with "no armour" treated as an armour variant. — [GameDev.net](https://gamedev.net/forums/topic/556056-how-to-design-diablo-style-sprites/)
- Max Schaefer: Diablo II was more complex because "the more parts there were, the more layering had to be done on the sprites". — [GameBanshee Hellgate interview](https://www.gamebanshee.com/kwr43)
- **Universal LPC Spritesheet Character Generator:** items can have n layers, each with its own z-position (needed for capes, some hair, some bodies). Definitions are JSON. Extended weapons have "front" and "back" layers drawn over and under the body. Credits are tracked per layer via CREDITS.csv. — [OpenGameArt thread](https://lpc.opengameart.org/comment/92785); [OpenGameArt](https://opengameart.org/comment/80415); [GitHub fork](https://github.com/EttienneS/Universal-LPC-Spritesheet-Character-Generator)
- Tooling: a Godot plugin keeps LPC layers separate for runtime modification. The Rust `lpcg` crate merges layer identifiers ("Order of layers is important"). — [OpenGameArt Godot plugin](https://lpc.opengameart.org/node/147777); [lib.rs lpcg](https://lib.rs/crates/lpcg)

### Inferences
- For an isometric 8-direction game, z-order of layers must vary per direction (a shield goes behind the body when facing away). Diablo II's per-direction ordering file reflects this. Encode `layerOrder[direction][frame]` or, better, use a per-pixel depth buffer from analytic depth (section 3) or 3D rendering (section 1), so order resolves itself.
- Palette swapping in browser: render sprites as 8-bit indices (R channel = palette index) into a texture, then a fragment shader does `texelFetch(paletteTex, ivec2(index, paletteRow))`. In Canvas 2D, keep a `Uint8Array` index buffer and a per-character `Uint32Array` palette and write `ImageData` via a `Uint32Array` view. Use a ramp per material (e.g. 4 to 6 shades, hue-shifted: shadows cooler and more saturated, highlights warmer). Then tiers, factions and elemental tints are just new palette rows. This is a widely used technique, so no specific citation was gathered.

### Gaps
- The COF (composite object file) format details (per-direction layer ordering) were not retrieved from a primary modding source.
- No specific palette-shader article was fetched. The palette-swap description above is general practice, not cited.

## 5. Procedural animation (skeletal, IK, gait, squash and stretch) and clean pixel-art rotation

### Takeaway
Use a 2D or 3D bone hierarchy with FABRIK or analytic two-bone IK for legs and foot planting. Multi-legged gaits use a planted/swinging contact state per foot and step along splines. If you rotate already-pixelated parts, use RotSprite-style (Scale2x ×3, rotate, downsample) or cleanEdge (MIT, shader, browser-based). MMPX (with JS and GLSL code) handles style-preserving 2× magnification and precomputed rotations. Better still, render rotated parts at the target resolution from vector or 3D sources, so no pixel resampling happens.

### Cited Findings
**IK and procedural gait**
- FABRIK (Aristidou and Lasenby, Graphical Models 73(5):243–260, 2011) is a heuristic iterative IK solver that addresses the cost and unrealistic poses of earlier methods. — [FABRIK page](https://www.andreasaristidou.com/FABRIK)
- Shipped and engine use: Unreal Engine has a FABRIK node for chains of at least 2 bones. A Rain World-style 2D student game uses FABRIK for its worm, and its spider's legs raycast for nearby surfaces. — [Unreal docs](https://dev.epicgames.com/documentation/unreal-engine/fabrik-animation-blueprint-in-unreal-engine?lang=zh-CN); [Univ. Tartu project](https://courses.cs.ut.ee/2025/cg/fall/Main/Project-ProceduralAnimation)
- PIKA: IK plus height maps decide leg positions, and legs animate along Catmull-Rom splines. Gait systems track whether each foot is "planted" or "swinging" and lock planted feet to prevent sliding. — [PIKA, TAMU](https://people.engr.tamu.edu/sueda/courses/CSCE450/2025S/projects/David_Herring/index.html); [MoCap Online IK guide](https://mocaponline.com/blogs/mocap-news/inverse-kinematics-games-guide)
- Unity's stock IK solvers lack functionality for anatomically correct humanoid agents. One paper applies FABRIK instead. — [VGTU paper](https://journals.vilniustech.lt/index.php/MLA/article/view/19216)

**Rotation and scaling of pixel art**
- **RotSprite** (by Xenowhirl) guesses pixel patterns to keep sprite features intact during rotation, and can also resize. The standard tool approach is upscale with a Scale2x-family filter, rotate with nearest-neighbour, then downsample. A Godot "RotSprite-like" GPU shader upscales with Scale2x on the GPU. — [Sonic Retro wiki](https://info.sonicretro.org/RotSprite); [godotshaders RotSprite-like](https://godotshaders.com/shader/rotsprite-like-algorithm-for-cleaner-pixel-art-rotation); [docs.rs rotsprite crate](https://docs.rs/rotsprite/^0.1.3)
- **cleanEdge** (Torcado): a pixel-art upscaling algorithm designed for rotation that prioritises lines and edges to avoid the jumbled pixels and broken lines of nearest-neighbour rotation. Options include 2:1 slopes (otherwise 45° only), "line width" (≈0.707 aligns slopes on the diagonal), and a "highest color" overlap priority (set it to the outline colour). MIT licence, shader source in a GitHub gist, runs fully in browser, with batch export of rotation frames. — [torcado.com/cleanEdge](https://torcado.com/cleanEdge/)
- Practitioners describe cleanEdge as "a massive step up" from RotSprite and better with outlines, though not perfect. A Playdate developer used Scale2x as a simpler stand-in that "works well enough at low resolutions". Astropulse sells "Clean Rotate" for Aseprite. — [MakeCode forum](https://forum.makecode.com/t/cleanedge-rotate-your-images-without-blurring-my-first-extension/38585); [Aseprite community](https://community.aseprite.org/t/cleanedge-rotation-algorithm-implementation/20371); [Playdate devforum](https://devforum.play.date/t/cleanedge-tool-to-create-clean-rotation/9903); [Astropulse](https://astropulse.itch.io/clean-rotate-for-aseprite)
- **MMPX** (Morgan McGuire and Mara Gagiu, JCGT): a 2× pixel-art magnifier that preserves the exact palette, transparency and single-pixel features, and reconstructs curves, diagonals and sharp corners. It runs in under 0.5 ms for a 64k-pixel screen on GPU or CPU. Open source in C++, **JavaScript** and GLSL ES. It enables high-quality rotation via precomputation at load time. The authors recommend EPX and base xBR for content with only rounded corners, and HQX or anti-aliased xBR for large palettes and gradients. — [Roblox Research MMPX page](https://about.roblox.com/publications/mmpx-style-preserving-pixel-art-magnification)

### Inferences
- **Two-bone IK** (thigh and shin, upper arm and forearm) via the law of cosines is exact and cheap. Use it for humanoids. Use FABRIK for spines, tails and multi-segment spider legs. For a Diablo-style iso game, solve in 3D world space (x, y on the ground and z up), then project, so feet plant correctly on the iso ground plane.
- Procedural gait recipe for N legs: each foot has a rest target relative to the body. When |foot − target| exceeds a step distance and the leg's opposite-phase partner is planted, start a swing along an arc (lerp plus a sin lift), with a duration that scales with speed. Body bob is sin(phase), and lean comes from acceleration. Squash and stretch: scale y by 1−k and x by 1+k at landing, with volume-preserving x = 1/√y.
- **Best for this project:** avoid rotating bitmaps at all. Since the sprites are already code-drawn, re-render each limb at its rotated angle from its vector definition (or 3D) directly at pixel resolution. That removes rotation artifacts entirely. Use RotSprite or cleanEdge only for hand-made bitmap parts such as weapon icons. Then pre-bake rotations at 16 to 32 angles at load time, as MMPX suggests, instead of per frame.
- Pixel-perfect thin lines for limbs: draw with integer Bresenham and then remove "L-corners" (the pixel-perfect line cleanup Aseprite applies: drop a pixel whose two neighbours form an L-shape). This avoids doubled-up pixels on diagonals. This is general knowledge and wasn't cited in this session.

## 6. Procedural sprite generators (Bollinger, zfedoran, academic and ML work)

### Takeaway
The classic Bollinger-style generator works like this. A hand-authored template mask with cell states (always empty, always border, random body/empty, random body/border) is randomised and mirrored. Empty cells adjacent to body cells become outlines, and the sprite is coloured with a sine brightness gradient. It is about 200 lines of JS and works well for small symmetric creatures and ships. For characters it is best used as a sub-generator (helmets, shields, insignia, monster heads) inside a structured, skeleton-based generator. Academic and ML sprite generation exists but isn't production-ready for consistent animated characters.

### Cited Findings
- zfedoran's pixel-sprite-generator (JS, Canvas) is based on Dave Bollinger's algorithm. A 2D mask is randomised, mirrored and drawn to a canvas. — [GitHub zfedoran](https://github.com/zfedoran/pixel-sprite-generator)
- Mask semantics: **-1** = always border, **0** = always empty, **1** = random empty/body (50%), **2** = random body/border (50%). Order: init all to -1, apply mask, randomise, mirrorX (default on), mirrorY (default on), generateEdges, render. — [pixel-sprite-generator.js](https://raw.githubusercontent.com/zfedoran/pixel-sprite-generator/master/pixel-sprite-generator.js)
- Outline rule: every empty (0) cell orthogonally adjacent to a body cell becomes border (-1). Diagonals are not outlined. — [pixel-sprite-generator.js](https://raw.githubusercontent.com/zfedoran/pixel-sprite-generator/master/pixel-sprite-generator.js)
- Colouring: pick a random gradient axis (vertical or horizontal). Saturation = rand × `saturation`, hue = rand. Per line along u, a new hue is chosen if |mean of 3 uniform(-1,1)| > 1 − `colorVariations`. Brightness = sin((u/ulen)·π)·(1 − `brightnessNoise`) + rand·`brightnessNoise`. Border cells are multiplied by `edgeBrightness`. Defaults: colored true, edgeBrightness 0.3, colorVariations 0.2, brightnessNoise 0.3, saturation 0.5. — [pixel-sprite-generator.js](https://raw.githubusercontent.com/zfedoran/pixel-sprite-generator/master/pixel-sprite-generator.js)
- Academic and ML: AI-based 2D sprite generation works include Coutinho and Chaimowicz 2022 and 2024, Saravanan and Guzdial 2022, Han et al. 2018 and Wu et al. 2022. Kuo et al. 2016 proposes generating animation frames. — cited in the [Pixelat3D related work](https://sol.sbc.org.br/index.php/sbgames/article/download/45414/45175/)

### Inferences
- Upgrading the Bollinger idea for ARPG characters: give each body-part slot (head, torso, pauldron, helmet crest, shield) its own small template mask with the 4 cell states, generate it, and attach it to a skeleton bone. Shading then comes from normals (section 3) rather than the sine gradient, and the outline from depth discontinuities rather than "every empty neighbour". Seeded RNG (e.g. mulberry32) makes monsters reproducible from an ID.
- Grammar or parametric approach: a character "DNA" (body proportions, limb counts, part choices, palette ramp IDs) is evaluated into a skeleton plus primitive list, then into the 3D, SDF or analytic renderer. That is more controllable than cellular automata for humanoids. Cellular automata are useful for organic textures (moss, rot, rock skin) inside part masks.

- GAN/VAE sprite papers were intentionally covered only by citation list. No results or quality data was gathered.

## 7. Pixel-art downscaling, depixelization, quantization and dithering

### Takeaway
To get good pixel art *from* high-res renders, plain nearest-neighbour or box downscaling plus naive quantisation gives noisy results. Content-adaptive methods do much better. Kopf et al. 2013 uses bilateral spatial+colour kernels that keep thin lines sharp and connected. Gerstner et al. 2012 jointly optimises SLIC superpixels and a palette in CIELAB. Both are heavier than real-time per-frame needs, but they are useful for offline baking or as inspiration for a cheap "dominant colour per cell" downsample. Depixelizing (Kopf and Lischinski 2011) goes the opposite way (pixel to vector) and is mostly relevant for upscaling.

### Cited Findings
- **Pixelated Image Abstraction** (Gerstner, DeCarlo, Alexa, Finkelstein, Singh; NPAR 2012): abstracts high-res images into very low-res outputs with reduced palettes. It solves the mapping of features and the reduced palette simultaneously, modifying SLIC superpixels (k-means-like iterative clustering over position and colour). The palette uses an adaptation of mass-constrained deterministic annealing [Rose 1998], working in CIELAB. A 2013 Computers & Graphics journal version adds user constraints. Source code is available. — [Princeton PIXL](https://pixl.cs.princeton.edu/pubs/Gerstner_2012_PIA/index.php); [GMU project page](https://cragl.cs.gmu.edu/pixelate/); [EG digital library](https://diglib.eg.org/handle/10.2312/PE.NPAR.NPAR12.029-036); [journal version](https://cragl.cs.gmu.edu/pixelate/journal.html)
- **Content-Adaptive Image Downscaling** (Kopf, Shamir and Peers; SIGGRAPH Asia 2013, ACM TOG 32, article 173): adapts each downsampling kernel's shape and position to local features. Kernels are a bilateral combination of a spatial Gaussian and a colour Gaussian. It keeps thin linear features sharp and connected, suits vector-to-pixel-art conversion, and can be combined with palette reduction. Pseudocode is published. Supplementary results compare against Gerstner 2012. — [Kopf project page](https://www.johanneskopf.de/publications/downscaling); [pseudocode PDF](https://johanneskopf.de/publications/downscaling/paper/pseudocode.pdf); [SIGGRAPH history](https://history.siggraph.org/?p=208338); [supplementary](https://johanneskopf.de/publications/downscaling/supplementary/index.html)
- Öztireli and Gross (SIGGRAPH 2015, Perceptual Downscaling) call Kopf 2013 state of the art with "excellent results for generating pixel-art images". — [Cambridge-hosted PDF](https://www.cl.cam.ac.uk/~aco41/Files/Sig15PerceptualDownscaling.pdf)
- **Depixelizing Pixel Art** (Kopf and Lischinski, SIGGRAPH 2011, TOG 30(4)): extracts a resolution-independent vector representation by building a similarity graph (pixels are nodes, edges join similar colours), resolving crossings with heuristics to make it planar, and fitting and optimising spline contours. The original is too slow for interactive use, and a GPU real-time version exists (Kreuzer, Kopf and Wimmer, TU Wien 2015). — [Kopf page](https://johanneskopf.de/publications/pixelart); [SIGGRAPH history](https://history.siggraph.org/?p=114686); [TU Wien poster](https://www.cg.tuwien.ac.at/research/publications/2015/KREUZER-2015-DPA/KREUZER-2015-DPA-Poster.pdf)
- Related: "Pixelating Vector Art" and "Pixelating Vector Line Art" (Waterloo and Eurographics) address vector to pixel conversion. A 2026 Waterloo thesis covers content-aware pixel-art rendering on pixels of multiple shapes. — [UWSpace](https://uwspace.uwaterloo.ca/handle/10012/8136); [EG](https://diglib.eg.org/items/3468d785-2fb6-498f-8947-e1fc587f6675/full); [Waterloo thesis](https://uwspace.uwaterloo.ca/items/226d47c6-6302-489e-a9ff-799fe90e301d)
- Pixelat3D's downsampling picks the **highest-priority texel** per block (artist priority map) rather than averaging, to keep readable features. Its power-of-two block sizes avoid mixels. — [SBGames paper PDF](https://sol.sbc.org.br/index.php/sbgames/article/download/45414/45175/)
- 3D-stable dithering: Pope 2017 uses a world-sphere-mapped dither matrix, which is stable under rotation but not translation. Johansen 2025 uses a surface-stabilised, camera-adaptive dither (video: youtu.be/HPqGaIMVuLs). — cited in the [SBGames paper PDF](https://sol.sbc.org.br/index.php/sbgames/article/download/45414/45175/)

### Inferences
- For a real-time browser renderer, the practical takeaways are:
  - (a) Render directly at target resolution (no downscale) when geometry is procedural. The sections 1 and 3 pipelines do this.
  - (b) If you supersample (e.g. render at 4× and reduce), use a *mode/majority* or *priority* reduction per block on material IDs, not an average. This is the cheap analogue of Kopf and Pixelat3D, and it avoids blended "mud" colours.
  - (c) Quantise lighting to a fixed per-material ramp instead of running a global palette quantiser every frame.
- Offline palette generation for procedural characters: k-means or median-cut in a perceptual space (CIELAB per Gerstner; OKLab is a common modern choice, uncited here) to derive ramps from reference art. Then hand-tune hue shift.
- Dithering: for moving characters, avoid screen-space ordered (Bayer) dithering, which "swims" over moving surfaces. If you use dither for 2-band transitions, anchor the pattern to sprite or object space (character-local pixel coordinates), in the spirit of the surface-stabilised methods above. Most commercial pixel-art characters use no dithering at ~50 px scale.

- No source was retrieved on OKLab-specific quantisation, median-cut versus k-means quality comparisons for sprites, or Bayer versus blue-noise dithering choices for pixel art. These recommendations are general knowledge and unverified in this session.
- The full Kopf 2013 algorithm parameters (EM iterations, kernel constraints) were not extracted, though the pseudocode PDF URL is listed above.
