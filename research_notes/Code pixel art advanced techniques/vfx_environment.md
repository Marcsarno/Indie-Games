# VFX and Environment Richness for a Palette-Indexed Dark-Fantasy Pixel Dungeon (270x480, ~51 colors, code-drawn)

Scope note: the strongest primary evidence here comes from the DevilutionX source code, an open-source reimplementation of Diablo 1 (read directly from GitHub master, Oct 2026). It shows how Diablo actually does banded lighting, palette blending, color cycling and wall cutaway with 8-bit indices. Pixel-art tutorial sites (Saint11, Slynyrd) were partly reachable; several "tutorial" search hits were SEO or spam mirrors and were not used. Concrete recipes that come from convention or my own engineering judgment, not from a source, are in the **Inferences** subsections and are labelled "(convention)" or "(design proposal)". Nothing in the Inferences was measured.

---

## 1. Pixel-art VFX: fire, torches, smoke, blood, magic, explosions, palette cycling, blend tables, flicker

### Takeaway
Diablo-era palette games get "glow", transparency and animated fire and lava almost entirely from **precomputed index-to-index lookup tables**: 16 light-level remap tables, a 256x256 50%-blend table, and D2's 25/50/75%, additive and multiply tables. They add **palette-index rotation** (color cycling) on top. A 51-color game can copy this exactly with tables a few KB in size, provided the palette is organized as **light-to-dark ramps**. That ordering is what makes shading by index offset work.

### Cited Findings

**Diablo 1 light tables (DevilutionX, primary source code)**
- There are 16 light levels: `LightsMax = 15`, `NumLightingLevels = LightsMax + 1`. Each light table is a 256-entry palette-index remap. The engine allows `MAXLIGHTS 32` dynamic lights and `MAXVISION 4` vision sources. — [DevilutionX lighting_defs.hpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/lighting_defs.hpp)
- Light tables are generated by **shifting indices within palette ramps**. The palette is walked in ramp blocks of sizes `{16,16,16,16,16,16,16,16,8,8,8,8,16,16,16,16,16,16}`. At shade `s`, each index maps to `rampStart + step + s*steps/16`; anything past the ramp's end becomes black (index 0). Table 15 is forced to all black ("Make last shade pitch black"). So Diablo's palette is laid out as contiguous bright-to-dark ramps, and darkening means "slide down the ramp". — [DevilutionX light_tables.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/light_tables.cpp)
- Falloff per light radius is a lookup table `LightFalloffs[radius][distance]`. Distance is measured in 1/8-tile units, and maxDistance = (radius+1)*8. Normal levels use **linear** falloff: `level = distance/maxDistance * 15 + 0.5`, and 15 (black) beyond the radius. Hellfire Nest and Crypt levels use **quadratic falloff with over-exposure**: `factor^2 * (radius*1.25) + (15 - radius*1.25)`, clamped at 0. — [DevilutionX light_tables.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/light_tables.cpp)
- Sub-tile light positioning uses a precomputed `LightConeInterpolations[8][8][16][16]` table of `sqrt(a^2+b^2)` distances for 8x8 sub-tile offsets. There is no runtime sqrt. — [DevilutionX light_tables.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/light_tables.cpp)
- **Emissive surfaces stay bright.** In Nest and Crypt levels, light-table entries 0–15 (the lava ramp) are set to identity in every table ("Make the lava fully bright"), so lava ignores darkness. — [DevilutionX light_tables.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/light_tables.cpp)
- **Animated lighting via cycling light tables.** In Hell levels, a custom ramp is written into indices 1–31 of each light table ("Blood wall lighting"). `lighting_color_cycling()` rotates entries 1–31 of every light table each tick, which animates the blood walls through the lighting itself. — [DevilutionX light_tables.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/light_tables.cpp), [DevilutionX lighting.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/lighting.cpp)
- Special-state remap tables exist alongside the light tables: `InfravisionTable`, `StoneTable` (stone-curse grey) and `PauseTable`, each a 256-entry index remap. — [DevilutionX lighting.h](https://github.com/diasurgical/devilutionX/blob/master/Source/lighting.h)
- The renderer specializes each scanline by light type: `FullyDark` fills black, `FullyLit` copies, `PartiallyLit` uses one table for the whole tile, and `PerPixel` uses a per-pixel lightmap. A comment notes the renderer builds "a special lightmap buffer to bleed light up walls". — [DevilutionX dun_render.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/render/dun_render.cpp), [DevilutionX scrollrt.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/render/scrollrt.cpp)

**Palette-indexed transparency and blending**
- DevilutionX builds `paletteTransparencyLookup[256][256]`. Each entry is the **nearest palette color (k-d tree search) to the RGB average** of colors i and j, i.e. a 50% blend. The table is symmetric (`[i][j] = [j][i]`) and `[i][i] = i`. A 16-bit variant blends two pixels against black in one lookup. — [DevilutionX palette_blending.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/utils/palette_blending.cpp)
- Transparent pixels are drawn as `dst = LUT[dst][src]`, with lighting applied to src first. A fully dark transparent pixel blends with index 0. — [DevilutionX dun_render.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/render/dun_render.cpp)
- **Diablo 2 PL2 files** store a 256-color palette plus precomputed transforms: alpha blends at 25%, 50% and 75% against every palette color, and 256-entry **additive** and **multiply** blend tables. — [OpenDiablo2 PL2 docs mirror](https://download.plaud.ai/OpenDiablo2/pl2). AbyssEngine's Go struct names the blocks differently: 14 "unknown variations", a "max component blend" table, darkened-color shift, and text colors. — [AbyssEngine pl2file](https://pkg.go.dev/github.com/OpenDiablo2/AbyssEngine/pkg/fileformats/pl2file). A d2mods forum post gives yet another block order (75/50/25%, then screen and luminance). — [d2mods.info](https://d2mods.info/forum/viewtopic.php?p=22693). **The sources conflict on the exact layout.** What all three agree on is that D2 used precomputed per-palette blend tables for several blend modes, including additive and screen-like modes.

**Color cycling (palette rotation)**
- DevilutionX `CycleColors(from,to)` rotates the logical and system palettes by one index **and rotates the rows and columns of the blend LUT in step**, so transparency stays correct while colors cycle. — [DevilutionX palette.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/palette.cpp)
- Measured cycle rates from the source:
  - Caves water rotates indices 1–31 every frame.
  - Crypt lava (15 colors) cycles in reverse every other frame, while the glow (16 colors) cycles every frame. The source comments: "the full animation has 240 frames before it loops".
  - Hive pond: bubbles (8 colors) and waves (7 colors) cycle every 3rd frame, giving "56 frames before it loops".
  
  Coprime ramp lengths give long loops from tiny data. — [DevilutionX palette.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/palette.cpp)
- Mark Ferrari's GDC 2016 talk "8 Bit & '8 Bitish' Graphics – Outside the Box" covers color cycling and palette shifting as a way to get background animation without frame-by-frame animation. — [GDC Vault](https://gdcvault.com/play/1023586/8-Bit-8-Bitish-Graphics)
- Ferrari used cycling for rain, snow, ocean waves, fog, clouds, smoke, waterfalls, streams and lakes in flat 640x480 single-palette images with no layers or alpha. Joe Huckaby's HTML5 port has a "BlendShift" mode that fades each color into its neighbor for in-between frames. For performance it **precomputes the offsets of pixels that use cycling indices and redraws only those**: a full redraw is 307,200 px per frame, which some browsers could not sustain. The port ran acceptably on an iPhone 3GS and iPad, but no fps figure is given. — [EffectGames: Old School Color Cycling with HTML5](https://www.effectgames.com/effect/article-Old_School_Color_Cycling_with_HTML5.html)

**Effect animation (fire, smoke, explosions)**
- Saint11 (Pedro Medeiros) publishes about 100 single-GIF, 512x512 pixel-art tutorials. Relevant titles include Fire, Explosion, SmokeSheet, Impact, DarkMagic, LightMagic, Electric, Blood, Goo, IlluminationTechniques, Shine and Darkness. The index page has no text, so I could not extract frame counts. — [saint11.art tutorials](https://saint11.art/blog/pixel-art-tutorials/)
- One explosion breakdown splits the effect into a large burst, a small burst, large smoke and small smoke, each with its own emitter. The smoke runs a linear animation **from fire colors to black, then dissolves**. — [r/PixelArtTutorials breakdown (mirror)](https://redlib.hbubli.cc/r/PixelArtTutorials/comments/1hkuqv1/breakdown_of_this_pixel_art_explosion_effect)
- Smoke "puffs out, grows slightly over a frame or two, then breaks into small clouds that vanish". — [Uppsala student devblog](https://babel.speldesign.uu.se/?p=33469). A critique suggests erasing smoke bit by bit for dissipation and giving it extra frames. — [AGS forums](https://www.adventuregamestudio.co.uk/forums/index.php?msg=520871)
- A commercial 1-bit 16x16 VFX pack makes most animations 8 frames, which is a common budget convention. — [1-Bit VFX Pack 1](https://sincpc.itch.io/1-bit-vfx-pack1)
- Dead Cells renders characters about 50 px tall from low-detail 3D, with no antialiasing, plus exported normal maps and a toon shader. A lighting system replaces hand-drawn shading per frame, and attack VFX "add movement, impact and strength" to pose-to-pose animation. The author lists flickering pixels as an unsolved artifact. — [Game Developer, Thomas Vasseur](https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-)

**Light flicker**
- Brogue treats torches as dungeon "features" with light parameters such as min and max radius, and colors cells with random variance. One reimplementation swaps in Perlin noise for smoother variance. — [anderoonies, Brogue generation 3](https://anderoonies.github.io/2020/11/14/brogue-generation-3.html)

### Inferences
- **Organize the 51-color palette as ramps (design proposal).** For example: 1 black, then about 6 ramps of 6–8 colors (stone grey-blue, warm flesh/wood, blood red, fire orange-to-yellow, sickly green/poison, arcane blue-violet), plus 2–3 UI or pure-highlight colors. Diablo's ramp-shift light tables then work as-is: `light[level][idx] = (idx - rampStart + shift(level)) < rampLen ? idx + shift : BLACK`. With 16 levels x 51 entries the table is **816 bytes**. If the game currently computes "banded lighting" per pixel arithmetically, switching to a table makes it one array read per pixel.
- **Blend tables for 51 colors are tiny (design proposal).** One NxN table is 51x51 = 2,601 bytes. Precompute these at boot: 50% average, additive (`min(255, a+b)` per channel, then nearest palette color), multiply, and optionally 25% and 75%. That is about 13 KB total, computed in <5 ms using nearest-color search in a perceptual space (OKLab or weighted RGB). Use additive for fire, magic, sparks and lightning cores; 50% for smoke, ghosts and wall cutaway; multiply for shadows and blood pools on stone.
- **Glow in indexed space (convention).** Draw the glow sprite with the additive LUT: `dst = ADD[dst][src]`. A soft radial falloff then needs only 2–3 glow indices, such as dark red, orange and yellow, and additive brightening of dark floor reads as light. You can also raise the light level locally by subtracting 1–3 bands in a radius around the projectile, which is what Diablo's dynamic lights do: missiles carry a light radius.
- **Fire and torch recipe (convention).**
  - Use 4–6 frames at 8–12 fps (about 83–125 ms per frame).
  - Shape it as a teardrop with a wide base and 1–2 detached "licks" that rise and vanish.
  - Ramp from the core outward: white/yellow, yellow, orange, red, dark red, then smoke grey.
  - Code-drawn variant: per-pixel "Doom fire". Keep a heat buffer, take `heat[x][y-1] = heat[x+rand(-1..1)][y] - rand(0..1)`, and map heat to the fire ramp. At torch size (8x16 px) this is about 128 cells, which costs nothing.
  - Alternatively, cycle 5–6 fire-ramp indices in a static flame sprite, Ferrari or Diablo-lava style, for zero per-frame drawing.
- **Flicker model (design proposal).** `radius(t) = base + A * (0.6*noise1(t*6) + 0.4*noise1(t*17))` with A about 0.5 tile. Quantize to Diablo-style 1/8-tile distance units so the band edges jitter by at most 1 band. Add a rare "gutter" (a 10% dip for 80–150 ms, about once every 2–5 s). Desynchronize torches with a per-torch noise seed. Pure `Math.random()` per frame looks like strobing; smooth noise (as Brogue's reimplementer chose) reads as flame.
- **Embers and sparks (convention).**
  - Single pixels, or 1x2 streaks along the velocity vector.
  - Spawn 1–3 per second per torch.
  - Velocity is about −10 to −20 px/s upward with sinusoidal x drift.
  - Life is 0.6–1.5 s, stepping down the ramp (yellow, orange, red, gone).
  - Hit sparks: 4–10 particles with radial velocity of 60–120 px/s and life 0.15–0.3 s, drawn additive.
- **Smoke (convention, consistent with the cited breakdowns).** Use 50%-blend circles 3–8 px across that grow by 1 px every 2–3 frames, rise slowly, and shift down the grey ramp. Dissolve them with an ordered (Bayer 4x4) threshold rising over the last 30% of life. Dithered dissolve fits a 51-color palette better than alpha.
- **Explosion timing (convention).**
  1. Frame 0: a 1–2 frame full-bright flash disk (white/yellow, additive).
  2. Frames 1–4: a fireball expanding along the fire ramp.
  3. Frames 4–10: a smoke ring that darkens and dithers away, plus debris particles.
  4. A floor scorch decal spawned at the end (see section 2).
  
  The cited breakdown's four emitters (big and small burst, big and small smoke) map directly onto this.
- **Blood (convention).**
  - *Spray:* 6–15 pixel particles in a 60–90° cone along the hit direction, with gravity in screen-y. On landing, each stamps 1–2 px of dark red into the persistent floor-decal layer.
  - *Pools:* grow over about 1 s using a precomputed noise threshold (pool radius threshold rises), drawn with the multiply LUT over floor.
  - *Drips:* only on walls. A 1-px dark red column that grows downward.
- **Lightning (convention).** Use a midpoint-displacement polyline (4–6 subdivisions) drawn 1 px in pure white with an additive blue fringe. Redraw it with a new seed every 2–3 frames for 4–8 frames total, flash the local light level to max for 1 frame, and add a branch with 30% probability per segment.
- **Healing and aura (convention).** Use rising pixel motes (green or gold) with sine drift, plus an isometric ellipse ring (2:1 aspect) on the floor. Its 3–4 dash pattern rotates via index cycling: assign ring pixels to 4 cycling indices so rotation costs nothing.
- **Dithered vs true alpha (inference).** True alpha needs RGB compositing, which breaks palette fidelity. Diablo resolved this with LUT blending into the palette. At 270x480 shown on a high-DPI phone, a 50% checkerboard is still visible as a pattern (each art pixel is 3–4 screen pixels), so the **LUT blend is the better default**. Reserve ordered dither for dissolves and fades, where the pattern itself reads as "disintegration".

## 2. Juice in effects: flash, particles, hit sparks, shockwaves, camera shake, decals, corpses, clarity vs chaos

### Takeaway
The best-documented juice primitives are trauma-based noise camera shake and the Vlambeer "small tweaks" stack (shake, muzzle flash, camera kick). For a dense ARPG the key decision is budget: brief additive flashes and sparks, **persistent baked decals** (blood, scorch, corpses) to accumulate history, and capped shake so the screen stays readable.

### Cited Findings
- Jan Willem Nijman's "The Art of Screenshake" (INDIGO / Control Conference, Amsterdam, 2013) starts from a dull shooter and applies about 30 small tweaks, including screen shake, muzzle flash and camera kick. With the same mechanics, the result "looked like a commercial game". — [Game Developer](https://gamedeveloper.com/design/vlambeer-co-founder-shares-advice-on-building-better-action-games), [Vlambeer Wikipedia](https://en.wikipedia.org/wiki/Vlambeer)
- Squirrel Eiserloh's GDC 2016 talk "Math for Game Programmers: Juicing Your Cameras With Math" covers camera shake. The common implementation credited to it uses a 0–1 "trauma" value and Perlin noise. — [GDC Vault](https://gdcvault.com/play/1023146/contactUs), [UnityCameraShake listing](https://awesome.ecosyste.ms/projects/github.com%2FIronWarrior%2FUnityCameraShake)
- Concrete parameters from Bevy's official 2D screen-shake example, which follows the talk:
  - `TRAUMA_DECAY_PER_SECOND = 0.5`: full trauma decays to 0 in 2 s.
  - `TRAUMA_EXPONENT = 2.0`: shake = trauma², so small hits are subtle.
  - `MAX_ANGLE = 10°` and `MAX_TRANSLATION = 20` px.
  - `NOISE_SPEED = 20`.
  - `TRAUMA_PER_PRESS = 0.4`.
  - x, y and rotation sample 1D Perlin noise at offsets t, t+100 and t+200.
  
  — [Bevy 2d_screen_shake.rs](https://github.com/bevyengine/bevy/blob/main/examples/camera/2d_screen_shake.rs)
- Dead Cells relies on VFX for the sense of impact in pose-to-pose attacks. — [Game Developer, Vasseur](https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-)
- DevilutionX has a per-frame palette-remap pathway (`PauseTable`, `StoneTable`, `InfravisionTable`). The same mechanism supports full-screen flashes and tints, such as red on damage or white on lightning, by swapping a 256-entry remap for a few frames. — [DevilutionX lighting.h](https://github.com/diasurgical/devilutionX/blob/master/Source/lighting.h)

### Inferences
- **Shake at 270x480 (design proposal).** Scale Bevy's 20 px max to about **4–6 art pixels** max translation and **no rotation**, since rotation breaks the pixel grid. Round the offset to integers. Use trauma² and 0.8–1.5/s decay. Suggested trauma per event:
  - Normal hit received: 0.15
  - Crit dealt: 0.1
  - Explosion near the player: 0.4
  - Boss slam: 0.6
  
  Do not shake on every enemy hit the player deals, or Diablo-scale mob counts will cause constant jitter.
- **Hitstop (convention).** Freeze attacker and target 2–4 frames (33–66 ms) on crits and kills only.
- **Flash (convention).**
  - Hit flash on the enemy sprite: replace every non-transparent pixel with white (or index-remap to the top of the ramp) for 1–2 frames.
  - Screen flash: apply a "brighten 3 bands" light-table offset globally for 1 frame on big explosions. Avoid pure white full-screen flashes on mobile, where they are uncomfortable and flash-sensitivity risky. Cap the rate at about 3 per second.
- **Shockwave (convention).** Draw an expanding isometric ellipse (rx = 2·ry) outline 1 px wide with the additive LUT, radius growing at about 150–250 px/s for 150–250 ms, plus 1 frame of dust particles kicked outward at the ring edge.
- **Decal persistence (design proposal).** Keep a per-level "floor decal" indexed buffer in world space, or one Uint8Array overlay per chunk of tiles. Stamp blood, scorch, cracks and ichor into it once, and the cost becomes zero per frame afterwards, since the floor is redrawn from tile + decal. Fade old decals by stepping them one band darker every N seconds, or keep them for the whole level, as Diablo leaves corpses. Scorch = multiply-LUT a dithered disk darker, plus 2–3 ember pixels that glow for 2 s. Cap corpses at about 30–60 per level, and fold older ones into the decal layer as a "bones" stamp.
- **Clarity vs chaos (inference).** Give priority tiers to effect brightness:
  1. Player-threatening hazards: brightest, highest-contrast, unique hue.
  2. Player's own attacks: medium, warm.
  3. Ambient and decor (embers, dust): the darkest 2–3 bands, never using the top of any ramp.
  
  Cap simultaneous particles (for example 300) and drop ambient particles first when over budget.

### Gaps
- I did not find primary data on how Diablo 2, Diablo 3 or PoE cap or prioritize effects for clarity. This is a known ARPG concern, but I found no citable designer statement within budget.
- I could not get the original slide list from the Nijman talk.
- Whether Eiserloh specifically recommends trauma² is unconfirmed from the talk itself; Bevy uses an exponent of 2.

## 3. Environment richness: tile variation, autotiling, wear, props, decals, AO, god rays, fog, fog of war, wall cutaway, atmospherics

### Takeaway
Richness comes from three cheap layers on a base tileset:
1. **Seeded per-tile variation and wear**: variants, cracks, discoloration, per-cell color variance.
2. **Correct edge logic**: blob/wang autotiling and wall-base occlusion.
3. **Animated light and color**: flicker, cycling water and lava, emissive surfaces.

Diablo-style wall cutaway is done per room region with a "transparent" flag. Only the upper part of walls between camera and player is blended, while wall bases stay opaque.

### Cited Findings

**Tile drawing and variation**
- Slynyrd's brick guidance for 16x16 tiles with 1 px grout:
  - Brick dimensions dividing evenly into 16 are 15, 7, 3 or 1 px.
  - Draw grout first, fill the bricks, then age with discoloration and damage on both bricks and grout.
  - Wall tops are much brighter than side faces, and bricks on side walls are shorter than on tops.
  - Use columns as universal corner pieces.
  - Keep drop shadows short, within one tile.
  - Make at least one variant of any heavily used texture, plus occasional cracked or discolored tiles, to fight visual fatigue.
  - Grout value (light vs dark) dramatically changes the feel.
  
  — [Slynyrd Pixelblog 45](https://www.slynyrd.com/blog/2023/7/21/pixelblog-45-bricks-walls-doors-and-more)
- Slynyrd also has isometric-specific guides (Pixelblog 41 and 54) and top-down tile guides (20, 43). — [Slynyrd catalogue](https://www.slynyrd.com/pixelblog-catalogue)

**Autotiling schemes (Boris the Brave)**
- *Marching squares*: 16 tiles indexed `TL + 2·TR + 4·BL + 8·BR` by corner solidity. Some sets add 2 diagonal tiles, for 18.
- *Blob*: all 8 neighbors, where a corner counts only if both adjacent edges are solid. The weighted sum is 0–255 but only 47 values occur, so use 47 tiles (+1 empty) via a 256-entry LUT.
- *Sub-blob*: 20 subtiles, 5 per quadrant (inner curve, outer curve, horizontal, vertical, solid), assembled per quadrant as in RPG Maker VX A2.
- *Micro-blob*: 13 subtiles.
- Sub-blob gives more variety from fewer drawings.

— [Boris the Brave, tileset roundup](https://www.boristhebrave.com/2013/07/14/tileset-roundup/)

**Per-cell variance (Brogue)**
- Brogue applies random color variance per cell and treats torches and small decorations as "features" placed by the level architect. A reimplementation used Perlin noise for smoother variance. — [anderoonies, Brogue generation 3](https://anderoonies.github.io/2020/11/14/brogue-generation-3.html)

**Wall cutaway and fog of war (DevilutionX / Diablo)**
- Diablo wall cutaway works per room region. Level generation assigns each room a `TransVal` region id (`DRLG_MRectTrans` over room rectangles). At render time a wall tile is drawn transparent if `TileHasAny(tile, TileProperties::Transparent) && TransList[dTransVal[x][y]]`, i.e. if its region is currently flagged active. — [DevilutionX gendung.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/levels/gendung.cpp), [DevilutionX scrollrt.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/render/scrollrt.cpp)
- Mask types are `Solid`, `Transparent`, `Left` and `Right`. The Left and Right masks blend only the upper triangle of a wall piece (a stair-stepped diagonal, 2 px per row) while "the lower 16 rows are opaque". This keeps wall bases solid and readable as the room boundary while the player shows through. Tiles flagged `TransparentLeft` or `TransparentRight` control which half gets the mask. — [DevilutionX dun_render.hpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/render/dun_render.hpp), [DevilutionX scrollrt.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/render/scrollrt.cpp)
- In original D2 (and D2R legacy graphics), most walls go transparent when the character is behind them. D2R's new graphics left some walls opaque, and players complained about losing sight of monsters. — [Blizzard forums](https://us.forums.blizzard.com/en/d2r/t/in-d2r-graphics-certain-walls-arent-transparent-when-your-character-is-behind-them/160254)
- Vision and exploration are separate from lights: `DoVision(position, radius, MapExplorationType doAutomap, visible)`, up to `MAXVISION 4` sources, with `MaxCrawlRadius = 18`. The vision crawl marks tiles visible and explored for the automap. Unlit-but-explored tiles render dark via the light level, and `DoUnVision` clears with radius+2 "to prevent leaving stray vision tiles". — [DevilutionX lighting.h](https://github.com/diasurgical/devilutionX/blob/master/Source/lighting.h), [DevilutionX lighting.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/lighting.cpp)
- Lights are updated incrementally. Each light un-lights its old area (radius+2, to cover diagonal moves) and re-lights only when `hasChanged`, so the tile lightmap is not recomputed globally every frame. — [DevilutionX lighting.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/lighting.cpp)

**Animated environment**
- Diablo animates environments mostly through **palette cycling**: cave water, crypt lava and glow, hive ponds and bubbles, Hell blood walls. — [DevilutionX palette.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/palette.cpp), [light_tables.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/light_tables.cpp)
- Ferrari used cycling for fog, smoke, rain, waterfalls and streams. — [EffectGames](https://www.effectgames.com/effect/article-Old_School_Color_Cycling_with_HTML5.html)

### Inferences
- **Seeded variation (design proposal).** For every floor cell, `h = hash(x, y, levelSeed)`. Use the bits for:
  - variant index (3–4 base variants);
  - a 15% chance of a crack overlay;
  - 8% moss, only on cells adjacent to walls or water;
  - 5% rubble or bone prop;
  - per-cell ±1-band brightness offset (Brogue-style variance, but quantized to palette bands).
  
  Use low-frequency value noise, not white noise, for moss and grime so it clusters into patches.
- **Wear rules (convention).**
  - Cracks start at tile edges or corners: random walk, 3–8 px, darkest band, with a 1-px highlight on the lit side.
  - Chipped bricks: remove a 1–2 px corner and replace it with the grout color.
  - Moss and grime gather at wall bases and in grout lines, i.e. low and in crevices.
  - Wear concentrates near doorways and on corridor centerlines, as traffic.
- **Props and clutter (convention).** Place by rules, not uniformly:
  - Against walls: barrels, crates, candles, skulls, chains.
  - In room corners: cobwebs, rubble piles.
  - Never in the 1-tile corridor centerline or doorway (to keep pathing readable).
  - Around light sources: candle clusters, wax drips.
  - Thematic rooms (library, crypt, torture) pick from a prop set, as Diablo themes rooms.
  - Density about 1 prop per 6–12 floor tiles in rooms, about 0 in corridors.
- **Ambient occlusion at wall bases (design proposal).** Bake into the floor: for floor pixels within 2–4 px (iso-projected) of a wall edge, drop 1–2 light bands, with an ordered-dither boundary. Diablo's "bleed light up walls" lightmap shows the related trick of lighting walls from the floor in front of them.
- **God rays and light shafts (design proposal).** Use a few static parallelograms from ceiling cracks, drawn with the additive LUT at 1 band. Add drifting dust motes inside (1-px, 50% blend, slow random walk, life 3–6 s) and a slow brightness breathing of ±1 band on a 3–5 s period.
- **Fog and depth darkening (inference).** In an isometric top-down view, "depth" is mostly distance from the light source. Diablo's linear 16-band falloff, and quadratic-with-overexposure for hot levels, are the two models to choose from. A per-level ambient floor (minimum light level for explored tiles, e.g. band 12–13 instead of 15) gives "remembered but dark" fog of war.
- **Fog of war (design proposal).**
  - Three states per tile: unexplored (black), explored-not-visible (fixed dark band plus optional desaturation remap), visible (lit by lights).
  - Reveal by a radius crawl from the player each time the player changes tile, not every frame.
  - Soften the reveal edge by dithering the boundary tile's pixels with a Bayer threshold.
- **Wall cutaway (design proposal, from the Diablo method).**
  - Tag each room in generation with a region id.
  - When the player's tile is in region R, or when wall tiles occlude the player sprite's bounding box, set `cutaway[R] = true`.
  - For wall tiles flagged "front-facing" (south and east faces in iso), blend only rows above about 1/3 of wall height with the 50% LUT, and keep the base row opaque.
  - Optionally fade over 4–6 frames by stepping LUT strength (25%, then 50%) if the D2-style 25/50/75 tables are built.
  - A cheaper alternative is a 50% checker mask.
- **Animated environment budget (convention).**
  - Water and lava: index cycling, at zero cost per pixel.
  - Candles: 2–3 frame flicker, plus the light-radius jitter above.
  - Drips: one pixel falling along a wall every 2–6 s, with a 2-frame splash.
  - Dust motes: 10–30 on screen.
  - Rats and bugs: rare.

### Gaps
- I did not reach sources for Darkest Dungeon environment art specifics, Blasphemous environment breakdowns, Dead Cells level-art layering, Oskar Stålberg / Townscaper procedural detail, Cogmind or Caves of Qud art approaches, or "dungeon decoration" generation articles. Time and tool budget ran out, so those recommendations above are convention, not cited.

## 4. Readability: value separation, characters and hazards in dark scenes, gameplay color coding, UI

### Takeaway
In dark palettes, readability comes from **value contrast and outline or linework, not hue**. Characters and hazards need luminance separation from the floor, plus reserved hues. Diablo's loot code (white, blue, yellow, then green and gold) works because it is limited, consistent and applied to text labels, not to sprites.

### Cited Findings
- Diablo 2 item names show blue for magic items and yellow for rare items. — [Battle.net classic D2 item pages](https://classic.battle.net/diablo2exp/items/magic.shtml)
- Community and wiki lists add white/grey for normal and low-quality items, green for set items and gold for uniques. Readability complaints about D2R's new colors (gold and uniques hard to tell apart, colorblind issues) show that **near-hue loot tiers are a known readability problem**. — [Blizzard D2R forum](https://us.forums.blizzard.com/en/d2r/t/bad-text-colors-for-items-rare-unique-and-runes/7096), [Diablo Wiki](https://di.diablowiki.net/Known_Items_Listing), [Blizzard D4 colorblind thread](https://us.forums.blizzard.com/en/d4/t/colorblind-person-here-please-change-the-text-colour-of-uniques-on-the-ground/174380)
- David Brevik said the Diablo loot colors "in a way" came from Angband. — [Game Informer](https://gameinformer.com/2019/05/18/the-surprising-origins-of-loot-rarity-colors)
- Darkest Dungeon's Chris Bourassa says strong linework lets him add unexpected hits of color without hurting readability, and that a defined set of style rules let him art-direct himself. — [GameSpot](https://www.gamespot.com:443/articles/the-gothic-sensibilities-of-darkest-dungeon/1100-6424880/). His GDC 2016 talk was "A Torch in the Dark: Using Creative Direction to Light 'The Darkest Dungeon'". — [GDC Vault](https://gdcvault.com/play/1023082/contactUs)
- Diablo's Nest and Crypt light tables keep the lava ramp fully bright in all light levels, so hazards stay visible in darkness. — [DevilutionX light_tables.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/light_tables.cpp)
- An `InfravisionTable` remap exists for showing monsters through darkness. — [DevilutionX lighting.h](https://github.com/diasurgical/devilutionX/blob/master/Source/lighting.h)
- D2 wall transparency exists so players can see monsters behind walls; D2R removing it on some walls drew complaints. — [Blizzard forums](https://us.forums.blizzard.com/en/d2r/t/in-d2r-graphics-certain-walls-arent-transparent-when-your-character-is-behind-them/160254)

### Inferences
- **Value budget (design proposal).**
  - Floor and walls live in the bottom about 60% of each ramp, with top bands reserved.
  - Characters always get at least a 2-band lighter rim, or a 1-px dark outline against floor.
  - The player gets a minimum light level: never darker than band 8, using a "self light" radius as Diablo does with the player light.
- **Emissive and hazard indices (design proposal).** Mark some palette indices as "emissive" so all light tables map them to themselves, as Diablo does for lava. Use them for hazard telegraphs (red/orange floor warnings), enemy eyes, loot beams, and projectile cores. This guarantees hazards read at any light level with no per-effect code.
- **Hue reservation (design proposal).** Within ~51 colors:
  - Reserve 1 saturated hue family each for enemy danger (red-orange), player and ally magic (blue-cyan), poison (acid green), and loot (gold).
  - Keep environment ramps desaturated (grey-blue, brown).
  - Loot labels follow the Diablo code (white, blue, yellow, green, gold), but separate gold from yellow by **value and an outline or label background**, given the documented confusion. Ideally add a shape cue (icon or border style) for colorblind players.
- **UI over dark scenes (convention).** Use a 1-px black outline or drop shadow on all text and a dark 50%-LUT panel behind labels. Keep UI colors out of the environment ramps so UI never camouflages.
- **Enemy outline for the elite or targeted enemy (convention).** Use a 1-px colored outline (Diablo-like hover highlight). In indexed rendering this is an edge-detect pass over the sprite mask, done once per sprite frame and cached.

### Gaps
- I found no measured contrast thresholds for pixel-art readability on mobile.
- Darkest Dungeon's GDC talk content on lighting and readability was not accessible as text.
- There is no primary Blizzard statement on full D2 item color rationale.

## 5. Browser/JS feasibility at 60 fps on mobile

### Takeaway
At 270x480 (129,600 px) every technique above is feasible if it is **table-driven and incremental**: precomputed LUTs, baked decal and AO layers, recomputing lighting only when lights move or change band, and cycling indices instead of redrawing. The per-frame cost should be roughly one indexed-to-RGBA pass plus sprite and particle draws.

### Cited Findings
- The Huckaby color-cycling engine found a full per-pixel redraw of 307,200 px per frame too slow in some 2010-era browsers. Recording the offsets of cycling-index pixels and updating only those made it run "at a decent speed" on an iPhone 3GS and iPad. — [EffectGames](https://www.effectgames.com/effect/article-Old_School_Color_Cycling_with_HTML5.html)
- DevilutionX avoids per-pixel lighting where possible:
  - It specializes tiles into FullyLit (plain copy), FullyDark (fill), PartiallyLit (one table per tile) and PerPixel (lightmap).
  - It precomputes falloff and sqrt tables.
  - It updates lights incrementally (`hasChanged` and un-light/re-light).
  
  — [DevilutionX dun_render.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/render/dun_render.cpp), [light_tables.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/light_tables.cpp), [lighting.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/lighting.cpp)
- When cycling, DevilutionX rotates only the affected LUT rows and columns, not a full recompute. — [DevilutionX palette.cpp](https://github.com/diasurgical/devilutionX/blob/master/Source/engine/palette.cpp)

### Inferences (none measured; estimates from typed-array arithmetic)
- **Frame pipeline (design proposal).**
  1. Render all world layers into a `Uint8Array(129600)` index buffer, and a parallel `Uint8Array` light-level buffer at pixel or per-tile-quad resolution.
  2. Final pass: `out32[i] = palRGBA[light[lvl[i]][idx[i]]]`, writing a `Uint32Array` view on `ImageData`, then `putImageData` once and let CSS scale it with `image-rendering: pixelated`.
  
  That is about 130k iterations of 3 array reads, likely about 1–3 ms on a mid-range phone in a tight loop. This is an estimate; benchmark it on the target device.
- **Palette cycling cost (design proposal).** Cycling is **free** with this design: rotate the 51-entry `palRGBA` (or remap indices) before the final pass. No per-pixel tracking is needed, because the final pass already touches every pixel. Huckaby's dirty-pixel trick matters only if you skip the full pass.
- **Blend LUTs (design proposal).** 51x51 tables (2.6 KB each) fit in L1 cache. Additive and 50% blending of particles costs one read-modify-write per particle pixel. Even 300 particles x 9 px is about 2.7k ops, which is negligible.
- **Lighting (design proposal).** Compute the per-tile light level from lights only when a light crosses a 1/8-tile step or its flicker-quantized radius changes band (Diablo's approach). Interpolate per pixel within a tile using a precomputed pattern, or use a per-pixel distance LUT per light, in an offscreen light buffer at 1/2 resolution (135x240 = 32k cells). Flicker that changes band 8–12 times per second means about 10 light recomputes per second per torch, not 60.
- **Things to avoid per frame:**
  - Canvas 2D `globalAlpha` or `globalCompositeOperation` on many small sprites, because it breaks palette fidelity and costs draw calls.
  - Per-pixel `Math.random()` (use precomputed noise textures or hashes).
  - `getImageData` readbacks.
  - Allocating particles (use pooled struct-of-arrays Float32Arrays).
- **Bake once per level:**
  - Floor and wall tiles with variation, wear and AO into a level-sized index buffer, or per-chunk buffers if the level is large.
  - Decals stamped incrementally into that buffer.
  - Static god-ray masks.
  - Sprite outlines and hit-flash masks per frame.
- **WebGL alternative (inference).** Upload the index buffer as an R8 texture and the palette and light LUT as small textures, and do the final pass in a fragment shader. This is cheapest on GPU, but the CPU pass at this resolution is probably sufficient. Keep both paths behind an interface if mobile benchmarks are marginal.

### Gaps
- I found no measured benchmarks of JS typed-array full-screen passes on 2025–2026 mobile hardware within budget. The 1–3 ms figure is an unverified estimate and should be measured on target devices.
